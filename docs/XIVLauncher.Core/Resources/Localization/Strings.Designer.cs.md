## 1. Purpose

There is no hand-written code in this file. It is the output of `System.Resources.Tools.StronglyTypedResourceBuilder` (banner claim: version `"4.0.0.0"`, `:14`) over `src/XIVLauncher.Core/Resources/Localization/Strings.resx`, and its only job is to turn each `<data name="K">` entry of that table into a compile-time-checked property so that call sites read `Strings.GamePathSetting` instead of the string `"GamePathSetting"`. The generated form is what buys the fork two things: the key string is spelled once (in the resx), and a renamed or deleted key becomes a compile error at every consumer instead of a silent `null`.

The fork keeps this Windows-era mechanism (`.resx` + generated class) even though it is a Linux/ImGui port. Upstream's localization is a different mechanism entirely — CheapLoc (`lib/FFXIVQuickLauncher/src/XIVLauncher/App.xaml.cs:12` `using CheapLoc;`, `:389` `Loc.Setup(AppUtil.GetFromResources("XIVLauncher.Resources.Loc.xl.xl_<code>.json"))`, `:393` `Loc.SetupWithFallbacks()`, `:399`/`:403` `Loc.Setup("{}")` degenerate paths, `Loc.ExportLocalizable()` at `App.xaml.cs:259` behind the `--gen-localizable` CLI option declared at `App.xaml.cs:53`-`:54`, tables embedded as `XIVLauncher.Resources.Loc.xl.*` beside `lib/FFXIVQuickLauncher/src/XIVLauncher/Resources/Loc/`). Nothing in `src/` references CheapLoc and no fork file carries the marker prefix `_"…"` (0 files), so the fork has fully switched to the resx path while upstream has not; the two cannot be reconciled by editing this file.

`Resources/Localization` is also where the translations live: 15 `.resx` siblings (`Strings.resx` + `Strings.{de,es,fr,hu,it,ja,ko,nl,no,pt,ru,sv,tw,zh}.resx`, i.e. 14 locales) plus this one `.cs`. The rest of `src/XIVLauncher.Core/Resources/` is assets (§8), reached through other mechanisms.

## 4. Which table answers: culture selection

Every accessor passes `resourceCulture` as the `GetString` tag. That field (`:21`) is only ever written by the generated `Culture` setter (`:44`), and no file in `src/` assigns it (`grep` for `Strings.Culture` finds only the declaration inside this file), so **the tag is `null` at all 170 call sites**: resolution is delegated to whatever default locale the CLR picked for the process, not to a launcher decision.

Consequences, each verifiable in this checkout:

* The fork has **no language switch**. Upstream's knob is `LauncherLanguage? LauncherLanguage` (`lib/FFXIVQuickLauncher/src/XIVLauncher/Settings/ILauncherSettingsV3.cs:24`) plus the `:379`-`:399` setup block in `App.xaml.cs`; the fork's 41-member `ILauncherConfig` (`../../Configuration/ILauncherConfig.cs.md` §2) has no equivalent member, and the member was dropped wholesale (§6 of that doc lists `LauncherLanguage` among the 26 dropped upstream names).
* `Config.ClientLanguage` is **not** the UI language: it is the game client language (`Program.cs:113` default `ClientLanguage.English`, consumed at `MainPage.cs:226`/`:245`/`:343` for gate/status lookups, and hard-coded to `ClientLanguage.Japanese` at `MainPage.cs:185`) and never touches `resourceCulture`.
* The only locale-ish work in the fork is the *game child* env: `Program.cs:70` `public static string CType = CoreEnvironmentSettings.GetCType();` (`CoreEnvironmentSettings.cs:51` shells `locale -a 2>/dev/null | grep -i utf` and picks the first entry starting with `C.`, else `""`), applied at `MainPage.cs:613`/`:614` (`System.Environment.SetEnvironmentVariable("LC_ALL", Program.CType)` and `LC_CTYPE`) under `App.Settings.FixLocale == true` — after startup, after the UI was already built, and for the child process, so it does not decide which `.resx` table the launcher reads. That file's behaviour is spec'ed in `../../CoreEnvironmentSettings.cs.md` §"GetCType contract details and hazards".
* Therefore UI text depends on the launcher **process** locale at startup plus whatever translations the build embedded (§5). Nothing in this fork can offer the user a language choice at runtime, and a user changing `LANG` after startup cannot change the UI text it has already drawn.

## 9. Invariants and hazards

* **Invariant:** every accessor is `get`-only, `internal`, `static`, and `String`-typed; there is no key-name parameter anywhere in the class, so the whole catalogue is compile-time addressed and renaming a resx key breaks 179 call sites (this is the class' main value; the resx is not runtime-extensible).
* **Invariant:** the resx key set, accessor name set, and accessor order are identical across all 16 resx files; any drift (key added only to the base, key renamed in one locale) is exactly a missing-translation bug, and there is currently none.
* **Invariant:** `ResourceManager` is memoized (`:30`/`:31`/`:32`) and the class is stateless apart from `resourceCulture`, so the class costs one allocation for the manager and then a table lookup per read — cheap enough to call inline inside ImGui draw functions, which is how all 179 sites do it.
* **Hazard — the seven zero-difference locales.** `de/it/ja/no/pt/ru/sv` resx are byte-identical English; adding one to the file list changes nothing visible. A "translated the UI to German" change must produce a table that *differs*, and CI ("Update localization") will happily land a non-diffing one.
* **Hazard — `tw` (14 / 170) and `nl` (35 / 170) are partial**, so a Simplified-Chinese-flavoured or Dutch user sees mixed-language UI (translated titles, English bodies) with no indication of why. Nothing in code records the coverage percentage, so the numbers above are only re-derivable from the files.
* **Hazard — nothing in the fork picks a locale.** With `resourceCulture == null` at every read, the language follows the process default; and because `Program.cs` never assigns `Strings.Culture`, `FixLocale` (which only sets a child env var) is not a substitute. A Deck UI in French therefore depends on whatever the host/toolkit defaults produce — and there is no in-app override at all. The fork's own language state is only recorded in the config as `ClientLanguage` (which controls the game client, not the launcher).
* **Hazard — un-localized literals bypass the catalogue.** `LauncherApp.cs:188`'s default `title = "XIVLauncher"`, `LauncherApp.cs:208` (`"Unknown error - please check logs."`), `LauncherApp.cs:213` (`"Task was canceled."`), `SettingsTabTroubleshooting.cs:26` (`"Hack Disabled. Could not find a UTF-8 C locale. You may have to set LC_ALL manually if LANG is not a UTF-8 type."`), `Program.cs:139` (`"English"`) all ship English text outside the resx. Catalogue coverage ≠ UI coverage.
* **Hazard — a `null` read is unchecked.** `GetString` yields `null` for a key not present in the compiled-in table; no site tests a `Strings.*` read for `null` (`grep` finds no comparison of a `Strings.X` against `null`), so a drifted key would be fed straight into `ImGui.Text`/`SettingsEntry` label slots — in ImGui bindings, a `null` `char*` is a crash/empty-text path, not a diagnostic. This is why the class' compile-time addressing is only a partial safety net: it protects names, not table completeness.
* **Hazard — the generated file is not hand-editable in practice.** The banner (`:1`-`:8`) plus csproj `:87` `<LastGenOutput>` and `:114` `<AutoGen>True</AutoGen>` mean the next resource-compiler pass rewrites the file. Editing it (e.g. to hard-code a language) is overwritten; and because the 170 accessor bodies are all identical modulo the key, a manual edit can also silently desync the accessor name from the resx key (0 such mismatches today, all names == keys).
